# ETL 本体管理技术选型文档

## 1. 文档依据

- 依据文档：《本体管理功能规划.md》
- 目标：选定图数据库、后端服务、管理端与可视化技术栈，并给出部署与集成方式。

---

## 2. 技术选型总览

| 层次         | 选型              | 说明 |
|--------------|-------------------|------|
| 图数据库     | **Neo4j**         | 成熟图库，Cypher 表达力强，适合本体关系与路径查询。 |
| 本体服务后端 | **Node.js + TypeScript**（与 ai-service 同栈） | 复用现有技术栈，与 jupyterlab-amphi / ai-service 一致。 |
| 图库驱动     | **neo4j-driver**（官方） | 官方 Node 驱动，支持 Bolt 协议。 |
| 管理端 + 可视化 | **Web 单页应用**：React + TypeScript + 图可视化库 | 与 pipeline-editor 技术栈一致，可复用 UI 组件。 |
| 图可视化     | **Cytoscape.js** 或 **React Flow** | 均可展示节点与边；React Flow 与现有编辑器一致，优先考虑。 |

---

## 3. 图数据库选型：Neo4j

### 3.1 选型理由

- **关系建模自然**：节点即实体（Component、Parameter、DataType、Category），边即关系（HAS_PARAMETER、CAN_FOLLOW 等），与本体模型一一对应。
- **查询能力**：多跳路径、邻居展开、按类型/属性过滤，Cypher 表达简洁，便于实现 F-VS-4（关系路径查询）与 F-AI-1（按类型查可连接组件）。
- **生态与运维**：社区版可满足开发与中小规模部署；企业版支持集群与备份，便于后续扩展。
- **替代方案**：JanusGraph、ArangoDB 等也可建模图，但 Neo4j 在「属性图 + Cypher」场景下文档与案例更丰富，与「本体 + 关系」需求最贴合。

### 3.2 部署方式

- **开发/测试**：Docker 运行 Neo4j Community，端口 7687（Bolt）、7474（HTTP）。
- **生产**：可按需使用 Neo4j Aura 或自建 Neo4j Enterprise，与本体服务通过 Bolt 连接。

### 3.3 与现有系统关系

- 本体服务作为**独立服务**或**ai-service 内模块**连接 Neo4j；图库仅被本体管理端与 ai-service 使用，不替代现有关系型 DB（若存在）。

## 4. 本体服务后端

### 4.1 技术栈

- **运行时**：Node.js 18+
- **语言**：TypeScript
- **框架**：Express 或 Fastify（与 ai-service 保持一致：若 ai-service 为 Express，则本体 API 可合并到 ai-service 或独立 Express 服务）。

### 4.2 模块划分

| 模块           | 职责 |
|----------------|------|
| **Ontology API** | 提供 REST：组件/参数/关系/类型的 CRUD，以及 F-AI-1 所需「按类型查组件」「拉取参数 Schema」等。 |
| **Neo4j 访问层** | 封装 neo4j-driver：连接池、会话管理、Cypher 执行与结果映射。 |
| **本体模型层**   | 定义节点/关系类型常量、DTO、与 components-metadata 的映射与导入逻辑。 |
| **权限与审计**   | 若需要 F-SYS-1/F-SYS-2：JWT 或 Session + 操作日志表或写回 Neo4j。 |

### 4.3 关键 API 设计（概要）

- `GET/POST/PUT/DELETE /ontology/components`：组件 CRUD。
- `GET/POST/PUT/DELETE /ontology/parameters`：参数 CRUD（或挂载在组件下 `/ontology/components/:id/parameters`）。
- `GET/POST/PUT/DELETE /ontology/relationships`：关系 CRUD。
- `GET /ontology/graph`：为前端图可视化返回节点与边（可带筛选）。
- `GET /ontology/search?q=...&type=...`：搜索（F-VS-3）。
- `POST /ontology/path`：关系路径查询（F-VS-4）。
- `GET /ontology/ai/components-by-io?inputType=...&outputType=...`：供 AI 服务使用的「按输入输出类型查组件」（F-AI-1）。

## 5. 管理端与可视化前端

### 5.1 技术栈

- **框架**：React 18+，TypeScript。
- **构建**：Vite 或与 jupyterlab-amphi 一致的 build 配置。
- **UI 组件**：Ant Design 或与 pipeline-editor 一致（如已有 antd），保证列表、表单、搜索、分页等体验统一。
- **图可视化**：
  - **推荐**：**React Flow**（与 pipeline-editor 一致），可复用节点/边样式与交互，展示 Component–Parameter、Component–Component 等关系。
  - **备选**：Cytoscape.js，图算法与布局更丰富，但需额外封装与 React 集成。

### 5.2 页面结构建议

| 页面/区域       | 功能 |
|-----------------|------|
| **本体管理首页** | 左侧树/列表（按 Category 或类型筛选），右侧为图视图或列表视图切换。 |
| **组件管理**     | 组件列表 + 筛选/搜索；点击进入组件详情：基本信息 + 参数列表 + 关系列表，可编辑。 |
| **关系管理**     | 关系列表（可按类型筛选）；支持新增/编辑「CAN_FOLLOW / ACCEPTS_INPUT / PRODUCES_OUTPUT」等。 |
| **图可视化**     | 全图或子图展示；搜索高亮、点击节点高亮邻居、路径查询结果高亮。 |
| **导入/导出**    | 上传 YAML/JSON 或触发「从 components-metadata 同步」；导出当前图数据。 |

### 5.3 部署方式

- 开发：独立 dev server（如 localhost:3000），通过 CORS 访问本体 API（或 ai-service 代理）。
- 生产：静态资源部署至 Nginx 或与 JupyterLab 同一域名下；API 与 ai-service 或本体服务同域或配置反向代理。

## 6. 数据模型与 Neo4j 建模建议

### 6.1 节点标签（Label）

- `Component`：id, name, description, category, pipelineType（对应前端 type）。
- `Parameter`：id, name, paramType, defaultValue, required, description（options 可存 JSON 字符串或单独节点）。
- `DataType`：id, name（如 pandas_df, documents）。
- `Category`：id, name（如 inputs, transforms, outputs）。

### 6.2 关系类型（Relationship Type）

- `HAS_PARAMETER`：(Component)-[:HAS_PARAMETER]->(Parameter)
- `ACCEPTS_INPUT`：(Component)-[:ACCEPTS_INPUT]->(DataType)
- `PRODUCES_OUTPUT`：(Component)-[:PRODUCES_OUTPUT]->(DataType)
- `CAN_FOLLOW`：(Component)-[:CAN_FOLLOW]->(Component)
- `BELONGS_TO_CATEGORY`：(Component)-[:BELONGS_TO_CATEGORY]->(Category)
- `PARAMETER_TYPE`：(Parameter)-[:PARAMETER_TYPE]->(DataType) 或属性表达
- `OPTION_OF`：(Option)-[:OPTION_OF]->(Parameter) 可选，或 options 存 JSON。

### 6.3 与 components-metadata 的对应

- 从 `components-metadata.md` 或等价 JSON 解析：每个组件 → 一个 `Component` 节点；每个 parameter → 一个 `Parameter` 节点 + `HAS_PARAMETER`。
- `default`、`options`、`required` 存为 Parameter 属性或通过关系表达；DataType 与 Category 可从现有 type/category 枚举或配置文件初始化。

## 7. 与 ai-service 的集成方式

### 7.1 方式 A：本体 API 独立服务，ai-service 通过 HTTP 调用

- 本体服务单独部署，提供上述 REST。
- ai-service 在 generate/validate 时请求「按输入输出类型查组件」「拉取参数 Schema」等，无直接依赖 Neo4j。
- **优点**：职责清晰，图库与 AI 服务解耦。**缺点**：多一次网络调用。

### 7.2 方式 B：本体模块内嵌 ai-service

- 在 ai-service 内增加 `ontology` 模块（Neo4j 客户端 + 封装），对外仍为 REST；GraphBuilder/Validator 内部直接调 ontology 模块而非 HTTP。
- **优点**：延迟低、部署简单。**缺点**：ai-service 与图库耦合，需同时配置 Neo4j 连接。

**建议**：先采用 **方式 B**（内嵌模块），便于快速迭代；若后续本体服务需被多系统复用，再拆成独立服务并改为 HTTP 调用。

## 8. 开发顺序建议

1. **Phase 1：图库与基础 API**
   - Neo4j 本地/Docker 搭建。
   - 本体模型（节点/关系）在 Neo4j 中建索引与约束。
   - 实现 Ontology API（CRUD + 从 components-metadata 导入）。

2. **Phase 2：管理端 CRUD 与列表**
   - 管理端项目初始化（React + TS + Ant Design）。
   - 组件/参数/关系的列表与表单增删改查，调用本体 API。

3. **Phase 3：图可视化与搜索**
   - 图视图（React Flow）：从 API 拉取节点与边并渲染。
   - 搜索接口与前端搜索框，结果在图视图高亮或定位。
   - 关系路径查询 API + 前端「路径查询」入口与结果高亮。

4. **Phase 4：AI 集成**
   - 在 ai-service 中接入本体模块（按类型查组件、拉取参数 Schema）。
   - GraphBuilder 使用本体数据做节点选择与连边；Validator 使用本体做类型与关系校验。

5. **Phase 5（可选）：权限与审计**
   - 登录与角色；写操作审计日志。
